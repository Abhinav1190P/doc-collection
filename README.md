# Document Collection

A screen for a tax accountant: what's outstanding for a client, what's come in, and what needs a human look.

## Stack

Flask, SQLAlchemy, SQLite, server-rendered Jinja templates, pytest. SQLite because this only needs to run on one machine with zero setup — no server to install or start.

## Running it

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements-dev.txt
python fixtures/make_fixtures.py
python seed.py
python run.py
```

Open `http://localhost:5000`. The seed script builds a Rivera household (from the assignment's example) and runs its documents through the system, including the awkward cases — a wrong-year W-2, a W-2 for someone not in the household, and an unreadable scan — so the checklist and the review queue both have real content the moment you open it.

Run the tests with:

```bash
python -m pytest -q
```

## How the checklist gets derived

`app/derivation.py` has one function, `compute_implied()`, that looks at a household's people and disclosed employment and works out what should be on the checklist: a prior-year Form 1040, a government ID for the taxpayer and spouse, and one W-2 per job. Job count comes from actual employment records for the current tax year if any have been disclosed; otherwise it falls back to last year's count, on the assumption nothing's changed until told otherwise.

`reconcile()` is what makes this safe to re-run. It diffs the freshly-computed list against what's already stored and only inserts what's missing — it never touches a requirement the accountant has already acted on (satisfied, dismissed, marked wrong, or added by hand). A system-derived item that's still sitting untouched as "needed" and is no longer implied by current data gets auto-retired; anything the accountant has already made a decision about is left alone permanently. This is what lets a job change disclosed in March correctly add a second W-2 to Luis's checklist without disturbing anything already resolved for Ana.

## How documents get classified

There's no real OCR/ML model here — `app/classifier.py` extracts text from the PDF and guesses type, tax year, and owner from keywords and a couple of regexes, plus a hand-rolled confidence score. Below 70% confidence, or if the guessed tax year or owner doesn't line up with what's expected, the document goes to a review queue instead of being auto-matched — the assignment's "shouldn't be acted on without human review" rule. Fixtures for all three awkward cases (wrong year, unrelated person, unreadable scan) are generated by `fixtures/make_fixtures.py`, including one PDF that's genuinely just a rasterized image with no text layer at all.

## What I decided

- Government ID is required for the taxpayer and spouse, not dependents.
- One prior-year 1040 per household (joint filers share a return), not one per person.
- "Marked not needed" and "removed as wrong" are exposed as two separate accountant actions in the UI (different intent, worth keeping distinct for the audit trail) but behave identically to reconciliation — both permanently exclude that requirement from being re-derived.
- A W-2 requirement matches a document by employer name when one's extractable; otherwise it falls back to the next open slot for that person.

## What I'd do next

- Real people-matching (this uses exact substring match on full name — a nickname or a scanned name with an OCR typo would fail to match and land in review, which is the safe failure mode but not a great one).
- Multiple households sharing one document inbox, since in practice mail doesn't arrive pre-sorted by client.
- An audit log on the requirements table itself, not just current status — right now the "why was this retired" reasoning lives in a free-text note.
